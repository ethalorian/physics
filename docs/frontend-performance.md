# Frontend performance

## Reading-calendar startup

The calendar waits only for its syllabus and reading assignments. Quiz review counts load concurrently and update the existing review badge when available; they no longer hold the planner or its refresh indicator behind the initial spinner. Other dashboard views still wait for all three sources. Source errors, staff/read-only checks, abort handling, focus refresh, calendar save payloads and confirmed-content behavior remain intact.

An initial production visit directly to the calendar also emits `scope: "loading"` through the same bounded browser-performance endpoint. `SYLLABUS_LOAD_MS`, `READINGS_LOAD_MS`, `QUIZ_COUNTS_LOAD_MS` and `READING_COUNTS_LOAD_MS` measure each fetch through JSON parsing; their matching `_LOAD_ERROR` flags are 0 for success and 1 for failure. `CALENDAR_DATA_READY_MS` measures time from the initial fetch cycle until both required sources succeed; `CALENDAR_READY_MS` measures until the planner's first committed effect, including its component loading. Neither readiness metric is LCP or a guaranteed paint timestamp. Durations include hidden time. A zero error flag describes a successful HTTP/JSON read, not a separate content-validation result.

Loading observations use only the fixed `reading-calendar` category, coarse viewport and these numeric metrics; no identifiers, URLs, query strings, error messages, work or grades are sent. Existing DNT/GPC/role-preview opt-outs, 2 KiB validation and server limits apply. At most six batches are sent for the first fetch cycle per dashboard mount, with each metric sent once. Refreshes, cancellations and later class/view changes do not restart this budget; an entry through a different dashboard view is not mislabeled as calendar startup. Pending metrics flush on the existing timer or exit, so log ingestion can lag completion. A canceled request has no completion metric. Missing metrics can also mean opt-out, failure, unsupported collection or incomplete delivery.

Run the existing telemetry tests for ingestion validation and request limits.

The shared assignment-source resolver and existing Honors/passage/section guards retain the previous selection behavior. ## Passive browser observations

Production mounts invisible reporters in the root layout. No dependencies, stylesheet changes, storage identifiers or database writes are added. The existing `next/web-vitals` hook supplies document-level CLS, FCP, FID, INP, LCP and TTFB when supported. These remain attributed to the initial document category, even after client navigation. Each metric is sent at most once, using its latest pending value; this is an initial-session observation, not a continuous final-value ledger or a bfcache measurement system.

Separate view observations follow homepage, student gradebook, Results, teaching calendar, reading planner and assignment calendar categories. Every 30 visible seconds, on view exit or on page hide they summarize long-task count/total/maximum and observed event-interaction count/maximum, with visible observation duration. Hidden time is excluded. Long tasks use the browser's `longtask` entries (normally tasks over 50 ms). Event entries request a 16 ms minimum duration and deduplicate in memory by interaction ID, capped at 1,000 per interval. The interaction maximum is a diagnostic, **not INP**; the count is observed qualifying interactions, not every click. Unsupported observations are omitted rather than reported as zero.

Each document reporter sends at most six batches, and each tracked view mount at most twelve. View budgets restart only when the fixed view category changes, not for each student, class, search or filter parameter. Batches are best effort with no retry, and a failure cannot block normal use. Do Not Track, Global Privacy Control and role-preview sessions suppress collection. Observers, timers and listeners are cleaned up on unmount; observers and intervals also stop when the batch budget is reached.

The payload contains only schema version, document/view scope, a fixed route category, a coarse viewport bucket and allowlisted numeric metrics. It excludes URLs/query strings, student/account/class IDs, names, work, grades, DOM selectors, event targets and user-agent strings. Interaction IDs never leave memory. Requests omit credentials and referrers, use keepalive and have no cookie/local-storage writes.

`POST /api/browser-performance` accepts same-origin JSON with a strict, closed schema and a 2 KiB streaming body limit. It rejects unexpected fields, duplicate/unsupported metrics, nonfinite/negative/out-of-range values and mixed document/view metrics. It performs no authentication or database lookup. Accepted batches are logged as `[browser-performance]` with `sampleRate: 1`. A best-effort ceiling of 120 accepted batches per instance per minute bounds log volume; it is not a distributed/global rate limiter. Rejected content is never logged by application code.

## Reading the measurements

Use existing Vercel runtime logs filtered by deployment ID and `browser-performance`. These custom observations do **not** populate Vercel Speed Insights. Platform log retention and sampling limits apply; no new log drain or external analytics service is configured. `sampleRate: 1` describes client eligibility, not guaranteed delivery. Budgets, opt-outs, browser support, exits and the server ceiling can omit samples.

Compare matching route category, scope, metric and viewport bucket. Use `OBSERVED_MS` when comparing stall counts/durations across windows. Report sample counts and collection dates with any percentile, and do not merge view interaction maxima with document INP. Controlled fixtures establish rendering work avoided, not a production latency percentage. Production comparisons require representative organic traffic after release.
